# 01 — Product Spec

## What SearchBench is

SearchBench is a free, public, continuously-updated benchmark that measures how well the major web-search/retrieval APIs used by AI agents and RAG pipelines — Tavily, Exa, Brave Search API, Serper, You.com, Perplexity Sonar, Linkup, Seltz, and (pending pricing clarity) Search Router — actually perform, broken down by query type (breaking news, general facts, multi-hop research, code/technical docs, local/shopping, long-tail research). The benchmark is neutral: SearchBench has no commercial relationship with any vendor that would bias the score, publishes its methodology and query set openly, and re-runs weekly so the numbers reflect current reality rather than a one-time launch snapshot.

(1) It names nine vendors as the set being measured; that was the market survey. Five run — Exa, Perplexity, Serper, You.com and Linkup. Tavily and Brave are held back because their terms are broad enough to be read as covering third-party benchmarking and no written consent has been sought; Seltz and Search Router carry explicit bars. (2) "re-runs weekly" is a design intent, not a fact: `track_record.scheduled_weeks` is 0 and no scheduler-invoked run has landed. On top of the free benchmark sits the monetized layer, and the shape of that layer was revised on 2026-08-04 after the first real run. The revision is worth stating up front because it inverts what the earlier version of this document proposed.

**The paid product is the benchmark run against the customer's own traffic, not the public one.** A developer's query mix is not the 150 questions published here, and the ranking that matters to them is the one produced by their queries, their definition of a good answer, and their cost constraints. That evaluation — a private run against a sample of their production queries, scored by the same ensemble under the same methodology, delivered as a custom routing table and a spend model — is something no competitor can copy out of the free data, because the free data is about a different set of questions. It also prices honestly: it is consulting-shaped work with a deliverable, sold to someone who already knows they have the problem.

**The routing client is free and open source, and what is sold alongside it is the live score feed, the hosted query classifier, and the private evals.** Free open-source routers already exist, and a paid thin client competing against a free one is a losing position; a free client that everyone adopts and a paid feed that keeps it current is the position worth having. Owning the integration point beats competing with clones of yourself.

**What people renew for monthly is reliability, not scores.** Score-based routing is the differentiator on top; it is not the product. The recurring value is failover when a vendor rate-limits or goes down, latency-aware routing, response caching, spend caps, and query logs — the operational layer a team building on three search APIs otherwise hand-rolls. A team will churn off "we pick a slightly better vendor per query". They will not churn off the thing that keeps their agent answering when Vendor A starts returning 429s at 3am. See `05-architecture.md` for what that means concretely and `06-business-model.md` for how it is priced.

The benchmark remains the trust and attention engine (the mechanism speko.ai uses for voice AI, generalized to web search — see `02-competitive-landscape.md`); the difference is that the business is now three things sitting on it rather than one, and the highest-value of the three is the one that runs the harness on someone else's questions.

This is still a two-sided bet: the benchmark alone is a legitimate, fundable open-source/community project even if the commercial layer never scales (comparable precedent: LLM Stats, YC S2025, "Independent AI evaluations lab" — see `07-build-plan.md` and `09-sources.md`). The commercial layer is what turns it into a venture-scale business, following the same playbook as OpenRouter, Portkey, Not Diamond, and Martian in the adjacent LLM-routing space (see `06-business-model.md`).

## Why this, why now

Three things are true simultaneously as of 2026-07-30, and the combination is the actual thesis:

1. **Every vendor in this space is now publishing its own benchmark as marketing**, and every one of them wins the benchmark it publishes (Tavily's `tavily-search-evals` repo: Tavily 93.3% vs. everyone else lower; Seltz's "Dynamic News Search Benchmark": Seltz wins; Search Router's self-run SimpleQA table: Search Router #1; Quercle's head-to-head pages: Quercle wins; fastCRW's "200-query benchmark": fastCRW wins). This is strong, current, dated evidence that "prove it with numbers" has become a competitive requirement in this category — the market has already decided it wants benchmarks. Head-to-head comparisons are therefore not the gap, and claiming they are is a mistake this project made in early drafts and has corrected (see "The launch claim" below). The gap is that all of them are single-shot, single-judge, published by a party with an interest in the outcome, and unaccompanied by data anyone could use to check them.
2. **The infrastructure-plumbing problem just got solved by someone else, which sharpens rather than kills the opportunity.** LiteLLM shipped a native `/v1/search` endpoint unifying 12+ search providers with cost tracking (v1.79.0-stable, 2025-10-26; expanded in v1.81.0-stable, 2026-01-18), closing out the original GitHub issue (#15314) that first suggested this gap existed. But LiteLLM's own docs confirm the developer still has to manually name which vendor to call for every request — there is no quality score, no benchmark data, and no automatic per-query-type routing logic anywhere in what shipped. LiteLLM solved "one SDK for many vendors." Nobody has solved "which vendor is actually best for this query" — which is exactly SearchBench's wedge, and LiteLLM's proxy is now a plausible distribution/integration point for it rather than a competitor.
3. **No funded or launched product combines a neutral, ongoing, cross-vendor benchmark with a monetized router**, confirmed by an exhaustive sweep of YC's company directory, Product Hunt's Search category, Hacker News Show/Launch HN, GitHub, and vendor blogs as of 2026-07-30 (full detail in `02-competitive-landscape.md`). The closest analogs are either single-vendor products using benchmarks as marketing, or neutral benchmarks in adjacent verticals (Agentset.ai for rerankers/embeddings, Openbenchmarks.com for company-funding-data APIs, Rhumb's "AN Score" for generic API operational readiness) that validate the mechanism without competing directly.

## The launch claim — what is actually true, and what is not

Revised 2026-08-04. Earlier drafts of the pitch reached for a stronger claim than the evidence supports: that nobody had run these vendors head to head, that no neutral party was running the comparison. That is not true and it is trivially falsifiable, which makes it the worst possible sentence to lead with. Vendor-authored head-to-head comparisons exist and are listed in `02-competitive-landscape.md`; third-party comparison articles exist; Tavily's evaluation repository is public and MIT-licensed. A reader who knows the space will find one inside a minute, and having found it will discount everything else on the page — including the parts that are true and load-bearing.

**The defensible claim, and the one to lead with: the first continuously updated, multi-judge, open-data leaderboard for web-search APIs.** Every word in it does work, and each is checkable:

- **Continuously updated** — re-run on a schedule with the elapsed history published, as opposed to a snapshot dated the day a vendor launched something. This one is *not yet earned* and the site must not assert it until scheduled runs exist in the data; see the cadence rules in `CLAUDE.md`, which enforce this in code rather than leaving it to discipline.
- **Multi-judge** — three models from three different labs, with their disagreement published per category rather than averaged away. Every vendor self-benchmark surveyed uses a single judge or an undisclosed one.
- **Open data** — the query set, the per-judge scores, the costs and the latencies are exported under an open licence, so the ranking can be recomputed by anyone who disputes it. This is the part no vendor benchmark does, because a vendor publishing the data that would let you re-derive a worse ranking has no reason to.
- **Neutral** — no vendor pays anything, and the conflicts that do exist are disclosed rather than denied (`13-conflict-of-interest.md`).

**Link the prior comparisons directly.** The competitive landscape section of the site and any launch post should name and link the vendor self-benchmarks, including Tavily's, rather than gesture at "vendor marketing" in the abstract. Linking the work you are positioning against reads as confidence; omitting it reads as either ignorance or hope that the reader will not check. It also makes the actual argument sharper — the problem with Tavily's benchmark is not that it is dishonest, it is that it is Tavily's, run once, with a single judge, and that no data was published that would let anyone re-derive it.

## Target user (v1)

The primary user is an individual developer or small team building an AI agent, RAG pipeline, or LLM application who currently either (a) hard-codes one search vendor and never questions whether it's the right one for their query mix, or (b) has already hand-rolled a fallback/retry harness across 2-3 vendors out of frustration — the second group is a pre-qualified, already-in-pain design partner pool, identifiable via the commenters on LiteLLM issue #15314 and adjacent HN threads. This is explicitly a small-business/individual-developer payer, not an enterprise procurement sale — consistent with the founder's constraint of no enterprise network or sales motion.

## v1 scope (what actually ships first)

Ship small and real rather than broad and vaporware. The credibility of the whole product rests on the benchmark being genuinely continuous, not a single snapshot — so elapsed time running in public matters more than vendor coverage on day one.

**Benchmark v1** covers 4-5 vendors at launch (recommended: Tavily, Exa, Brave, Serper, Perplexity — the set with the clearest pricing, the most complete ToS visibility, and, critically, the set that does *not* include the two vendors with explicit contractual no-benchmarking clauses; see `03-legal-and-vendor-terms.md` before adding Seltz or Search Router), scored weekly across a 150-300 query set spanning the 6-category taxonomy defined in `04-benchmark-methodology.md`, graded by a 3-judge cross-family LLM ensemble, published as a public, sortable dashboard plus raw data export (JSON/CSV/Parquet).

**Corrected 2026-08-05.** The line above is left as written; the vendor list in it is wrong and was wrong on the day it was written. It justifies its five names as "the set that does *not* include the two vendors with explicit contractual no-benchmarking clauses" and cites `03-legal-and-vendor-terms.md` — but that document's own "Practical recommendation for v1" names a different five (Exa, Perplexity, You.com, Serper, Linkup) and says to approach Tavily and Brave for written consent *before* including them: Brave's ToS §2(b)(xvi) bars using content to "create, train, evaluate, or improve...services", and Tavily's §3.2(x) bars disclosing "any performance information or analysis" to third parties. The harness implemented `03`, not this line, and has since the first run. `src/vendors/adapters.py::REGISTRY` is the single gate and holds Serper, Exa, Linkup, You.com and Perplexity. Seltz and Search Router stay out until written consent is in hand.

**Router v1** is an open-source BYOK client whose first release is a reliability layer, not a scoring layer. The developer supplies their own API keys for whichever vendors they use; the client handles failover on rate limits and outages, per-vendor timeouts, latency-aware selection, response caching, spend caps, and a structured query log. Score-based routing is a policy plugged into that layer — one the client can run offline from a downloaded snapshot of the public scores, so the free client is genuinely useful with nothing bought. SearchBench never touches or resells the underlying vendor relationship. This is the only monetization architecture compatible with the vendor ToS constraints identified in `03-legal-and-vendor-terms.md` — no proxy-resale-markup model is viable given what Tavily, Exa, Brave, and You.com's terms all say about sublicensing.

The order matters and is deliberate: a reliability layer is useful on day one to a team using a single vendor, which is most teams, and it earns the right to make routing decisions later. A routing layer that leads with quality scores has to win an argument about the scores before it is useful at all.

**Private eval v1** is the first thing sold. A customer supplies a sample of their real queries (or a description precise enough to synthesize one), the harness runs them against every cleared vendor under the published methodology, and the deliverable is a scored table on their traffic, a recommended routing policy, and a modelled monthly cost under it versus their current spend. It uses the same runner, judges, and rubric as the public benchmark — the product is the questions being theirs, not a different method. Private eval data is never published, never merged into a weekly run, and never influences a public score (`13-conflict-of-interest.md`).

**Explicitly out of scope for v1**: enterprise SSO/VPC/custom-SLA deals, a hosted proxy that touches API keys server-side beyond what's needed to make the routed call, any vendor not yet cleared against `03-legal-and-vendor-terms.md`, and any claim of "continuously run" before the benchmark has actually accumulated multiple real weeks of public history.

## Naming — open decision, flagged not resolved

"SearchBench" is usable but not clean: a dormant (last updated 2024-08-30) open-source GitHub project literally named `search-bench` (by Talc, benchmarking consumer AI search chat products like Andi/You.com/Gemini) already exists in an adjacent-enough space to create real "didn't you know that already exists" friction, and the `.com`/`.ai`/`.dev` domain registration status could not be conclusively determined this session (see `03-legal-and-vendor-terms.md` for the full naming-clearance writeup). Two candidate alternatives were explicitly rejected as live conflicts: "SearchArena" (LMArena's actual, current, ICLR-2026-published product) and "QueryBench" (a live, conceptually near-identical database-query-engine benchmark). The cleanest alternative found is **SearchRef** (or spelled out, "Retrieval Referee") — no conflicting product, repo, or trademark signal was found for it. This spec uses "SearchBench" as the working name throughout because that's the name the research was scoped under, but the founder should treat the final public name as an open decision to close (via a real registrar WHOIS check and a real USPTO TESS search — not just web search) before buying a domain, filing a trademark, or launching publicly.

## Success criteria for the f.inc / YC pitch

Per `07-build-plan.md`, the thing that needs to be true by application time is not "SearchBench is a finished company" — f.inc's own framing is "tell us what you're building" and rewards early, in-progress applications. What needs to be true: a live public dashboard, several continuous weeks of real weekly-refreshed data (the actual differentiator versus every existing vendor snapshot), a working (even if minimal) router SDK, and ideally a handful of real early users pulled from the pre-qualified pain pool (LiteLLM issue commenters, relevant HN threads).
