# 05 — Architecture

This document is a recommended technical design, not a verified fact-finding result like the other docs — it synthesizes the constraints established elsewhere in this directory (BYOK-only monetization, weekly-refresh benchmark, LiteLLM's now-standard `/v1/search` schema, OpenRouter's routing precedent) into a concrete build plan a coding agent can act on. Treat it as a strong starting point to adapt, not a spec to follow blindly — the founder and Claude Code should feel free to revise as real implementation constraints surface.

## System components

**1. The benchmark runner.** A scheduled job (recommended: GitHub Actions on a public repo, which gives free, unlimited GitHub-hosted-runner minutes — confirmed via GitHub's own billing docs, versus $0.006-0.062/minute if run on a private repo) that, once a week, loads the current query taxonomy (`04-benchmark-methodology.md`), calls each cleared vendor's API for every query, stores the raw responses, and hands them to the judge pipeline. Running this on a public repo is not just cost-free — it's a credibility feature, since anyone can inspect the actual harness that's producing the scores, which is the whole point of being the neutral option in a category full of vendor self-benchmarks.

**2. The judge pipeline.** Three parallel LLM calls per (query, vendor-response) pair — one per model family (see `04-benchmark-methodology.md` for the specific bias-mitigation reasoning) — scoring against a pointwise rubric, with the position-swap and length-normalization mitigations built in from the start rather than retrofitted. Store every individual judge score, not just the aggregate, so a disputed result can be inspected down to which judge said what.

**3. The data store.** Recommended: Supabase (free tier plausible at MVP scale — 500MB DB, 5GB egress; Pro tier $25/month once real traffic arrives — 8GB DB, 250GB egress, includes a small compute credit). Schema should separate raw vendor responses, per-judge scores, and aggregated weekly scores into distinct tables from day one, since the raw layer is what gets exported publicly and the aggregate layer is what the dashboard and router both read from.

**4. The public dashboard.** A sortable, filterable view of current and historical scores by vendor and query category, plus a raw data export (JSON/CSV/Parquet) — the export matters as much as the dashboard itself, since "you can independently re-check our numbers" is the credibility claim that differentiates SearchBench from every vendor self-benchmark surveyed in `02-competitive-landscape.md`. Recommended: Vercel (Hobby tier is free but licensed for non-commercial use only; once this is a monetized product, budget for Vercel Pro at $20/user/month).

**5. The router client — a reliability layer first, a scoring layer second.** Revised 2026-08-04. The earlier version of this section designed the router as a quality-routing engine with everything else as a tie-breaker. That is backwards for two reasons. Commercially, quality routing is the part a customer can argue with and the part that stops being interesting once they have read the leaderboard once; the operational layer is what they use every day and renew for. Technically, quality routing is the part that depends on a classifier and a live score feed, so leading with it means nothing works until both do.

The architecture is still dictated by the legal constraint in `03-legal-and-vendor-terms.md`: it must be BYOK. The developer supplies their own API key per vendor; the client never holds or resells vendor access. Inside that constraint, the request path is a stack of layers, in the order they are worth building:

1. **Unified call and normalized response.** One call shape across every cleared vendor, matching the `/v1/search` schema (see below). Useful with exactly one vendor configured, which is the state most teams are in.
2. **Failover.** On a 429, a 5xx, a timeout, or a malformed response, fall through to the next vendor in the policy rather than surfacing the error. Per-vendor circuit breaker with a decaying error window, so a vendor having a bad ten minutes is deprioritized and then allowed back rather than blacklisted. This is the single feature most likely to be the reason someone installs the client, because it is the thing they are currently writing by hand at the moment their agent falls over.
3. **Budget control.** Per-key and per-period spend caps, computed from the same per-query costs the benchmark measures, with a configurable action at the cap (degrade to the cheapest vendor, or fail closed). Cost visibility is the complaint the benchmark's own first run surfaced most sharply; a router that can measure spend but not bound it solves the interesting half of the problem.
4. **Caching.** Content-addressed on the normalized query, with per-category TTLs — a breaking-news query must not be served from a six-hour-old cache, and a general-facts query almost always can. The benchmark already knows which categories are freshness-sensitive, which is a non-obvious advantage over a generic cache.
5. **Latency-aware selection.** Route on measured p50/p95 within the set of vendors that clear the quality bar, using both the benchmark's measurements and the caller's own observed latencies, which will differ by region and are the more relevant number.
6. **Query log.** Structured, local-first, per-request: vendor chosen, why, latency, cost, cache hit, failover events. This is the diagnostic surface and it is also the input a private eval needs — a customer with three months of logs is a customer who can be shown exactly what a different policy would have cost them.
7. **Score-based routing, on top.** Pick the vendor that scores highest for the detected category, with cost and latency as weights. This is the differentiator, and it sits at the top of the stack rather than at the bottom.

OpenRouter's provider-routing layer remains the blueprint worth copying for the mechanics: uptime filtering that deprioritizes rather than removes providers with recent outages, cost-weighted load distribution using inverse-square price weighting among stable providers, and a quality-tiering pass with price ordering applied only within a tier. The analogous design here uses the weekly benchmark score as the quality-tier signal, cost and latency weighting within a tier, and recent error rate to deprioritize a vendor mid-outage.

**5b. What is open source and what is sold.** The client is open source, permissively licensed, and fully functional offline against a downloaded snapshot of the public scores. Free open-source search routers already exist; shipping a paid thin client to compete with them is a losing position, and a free one that becomes the default integration point is worth more than either. What is sold is the part that cannot be forked: the **live score feed** (fresh weekly scores, per category, with the vendor-reliability series behind them), the **hosted classifier** (see below), and **private evaluations** (`01-product-spec.md`). The split is deliberate and should be visible in the repository layout from the first commit — a client that has to be rewritten later to carve out a paid surface will be rewritten badly.

**6. Query-category classification — local by default, hosted as an upgrade.** The router needs to detect which of the six taxonomy categories (or "none of the above, default policy") a query belongs to before applying category-specific routing. Ship a local classifier in the open-source client — an embedding-similarity match against the published seed queries, or a small local model — so the free client's routing is genuinely informed rather than crippled. The hosted classifier is the paid upgrade: better accuracy, updated as the taxonomy moves, and no local model to load. Classification accuracy directly determines whether a routing decision is informed or noise, so this is worth measuring against a labelled sample early, and worth publishing the accuracy of — a routing product that will not state its own classifier's error rate is asking for the same trust this project exists to make unnecessary.

## Integration and distribution strategy

Design the router's request/response shape to be schema-compatible with LiteLLM's now-standard `/v1/search` endpoint (`docs.litellm.ai/docs/search/`) rather than inventing a competing shape. LiteLLM has already solved and open-sourced the per-vendor request/response mapping problem for 12+ providers — reinventing that mapping wastes build time on a solved problem and makes SearchBench harder to adopt for anyone already on LiteLLM. The differentiated part SearchBench adds is entirely the routing *decision* (which vendor, based on what evidence), not the plumbing underneath it — positioning SearchBench's router as a routing-policy plug-in on top of LiteLLM's schema, or a drop-in alternative with the same interface, is both technically sensible and a plausible distribution channel (LiteLLM's own userbase is a warm audience already primed to want exactly this).

## Stack recommendation (given the founder's constraints)

Full-stack + ML/systems-capable solo founder, Apple Silicon Mac as primary hardware, rented cloud compute available, no dedicated infra budget. A pragmatic default: TypeScript/Node or Python for the runner and router API (either is fine given the founder's stated full-stack strength; Python has a slight edge if the judge-ensemble and classification logic end up wanting closer integration with ML tooling), Next.js for the dashboard (pairs naturally with Vercel), Supabase (Postgres) for storage, GitHub Actions for the weekly scheduled runner, and a simple background-job pattern (rather than an always-on server) for the runner itself, since it only needs to wake up once a week. Keep the router API itself as a lightweight, always-on service (a small always-on instance or a serverless function with reasonable cold-start behavior) since that's the piece real users will call synchronously.

## Build-order recommendation

Ship the runner and judge pipeline first, against a small (4-5 vendor) cleared list, and get real weekly data accumulating in public as early as possible — the elapsed-time credibility this buys compounds daily and cannot be caught up on later. Ship the dashboard second, as soon as there's at least a few weeks of real data to show (a dashboard with one week of data looks like a demo; a dashboard with six weeks of data looks like a running product). This sequencing is what the timeline in `07-build-plan.md` assumes.

Third is where the 2026-08-04 revision changes the order. Previously: ship the router SDK. Now: **ship the first private evaluation before the router client**, because it needs no new software — the harness already runs an arbitrary query set against every vendor — and it is the only step that produces revenue and a customer conversation in the same week. It also generates the input the router most needs: a real customer's query mix, which is the thing that says whether category-based routing helps them at all. Then ship the open-source client, reliability layers first in the order listed in component 5, with score-based routing last. The chicken-and-egg problem that used to justify deferring the router is smaller than it looked, because the reliability layer's value does not depend on the benchmark's track record at all.

## Open technical questions to resolve during build, not before

Exactly how aggressive the query-category classifier needs to be before routing decisions are trustworthy is an empirical question — start with a simple heuristic and measure before investing in anything more sophisticated. Whether to hard-cache vendor responses for a given (query, week) pair or re-fetch on every dashboard load is a cost/freshness tradeoff best resolved once real traffic patterns are visible. Rate-limit-aware fallback behavior (what the router does when a vendor's own rate limit is hit mid-request) needs concrete numbers from each cleared vendor's dashboard/docs that weren't fully available in this research pass for several vendors (see `03-legal-and-vendor-terms.md` open gaps) and should be confirmed directly against each vendor's developer documentation before the router's retry/fallback logic is finalized.
