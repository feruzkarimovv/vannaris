# 05 — Architecture

This document is a recommended technical design, not a verified fact-finding result like the other docs — it synthesizes the constraints established elsewhere in this directory (BYOK-only monetization, weekly-refresh benchmark, LiteLLM's now-standard `/v1/search` schema, OpenRouter's routing precedent) into a concrete build plan a coding agent can act on. Treat it as a strong starting point to adapt, not a spec to follow blindly — the founder and Claude Code should feel free to revise as real implementation constraints surface.

## System components

**1. The benchmark runner.** A scheduled job (recommended: GitHub Actions on a public repo, which gives free, unlimited GitHub-hosted-runner minutes — confirmed via GitHub's own billing docs, versus $0.006-0.062/minute if run on a private repo) that, once a week, loads the current query taxonomy (`04-benchmark-methodology.md`), calls each cleared vendor's API for every query, stores the raw responses, and hands them to the judge pipeline. Running this on a public repo is not just cost-free — it's a credibility feature, since anyone can inspect the actual harness that's producing the scores, which is the whole point of being the neutral option in a category full of vendor self-benchmarks.

**2. The judge pipeline.** Three parallel LLM calls per (query, vendor-response) pair — one per model family (see `04-benchmark-methodology.md` for the specific bias-mitigation reasoning) — scoring against a pointwise rubric, with the position-swap and length-normalization mitigations built in from the start rather than retrofitted. Store every individual judge score, not just the aggregate, so a disputed result can be inspected down to which judge said what.

**3. The data store.** Recommended: Supabase (free tier plausible at MVP scale — 500MB DB, 5GB egress; Pro tier $25/month once real traffic arrives — 8GB DB, 250GB egress, includes a small compute credit). Schema should separate raw vendor responses, per-judge scores, and aggregated weekly scores into distinct tables from day one, since the raw layer is what gets exported publicly and the aggregate layer is what the dashboard and router both read from.

**4. The public dashboard.** A sortable, filterable view of current and historical scores by vendor and query category, plus a raw data export (JSON/CSV/Parquet) — the export matters as much as the dashboard itself, since "you can independently re-check our numbers" is the credibility claim that differentiates SearchBench from every vendor self-benchmark surveyed in `02-competitive-landscape.md`. Recommended: Vercel (Hobby tier is free but licensed for non-commercial use only; once this is a monetized product, budget for Vercel Pro at $20/user/month).

**5. The router SDK/API.** This is the monetized layer, and its architecture is dictated entirely by the legal constraint in `03-legal-and-vendor-terms.md`: it must be BYOK. The developer supplies their own API key per vendor they want available; SearchBench's router never holds or resells vendor access itself. On each request, the router either applies the developer's own explicit policy (e.g., "always use Brave for general facts, Perplexity for anything time-sensitive") or, more valuably, an automatic policy driven by the live benchmark scores — pick whichever cleared vendor currently scores highest for the detected query category, with cost and latency as secondary tie-breakers. This mirrors OpenRouter's own architecture closely enough to be worth copying deliberately: OpenRouter's provider-routing layer uses uptime filtering (deprioritize, don't fully remove, providers with recent outages), cost-weighted load distribution using inverse-square price weighting among stable providers, and a separate quality-tiering pass for tool-calling reliability, with price ordering applied only within a quality tier. SearchBench's analogous design: use the weekly benchmark score as the quality-tier signal (replacing OpenRouter's tool-calling-reliability heuristic), apply cost/latency weighting within a tier, and use recent-error-rate to deprioritize (not hard-exclude) a vendor experiencing a live outage.

**6. Query-category classification.** The router needs to detect which of the six taxonomy categories (or "none of the above, default policy") an incoming query belongs to before it can apply category-specific routing. A cheap classification pass (a small/fast LLM call, or a simpler heuristic/embedding-similarity classifier against the taxonomy's seed queries) sits in front of the routing decision. This is a genuine build decision point worth prototyping early, since classification accuracy directly determines whether the routing decision is actually informed or just noise.

## Integration and distribution strategy

Design the router's request/response shape to be schema-compatible with LiteLLM's now-standard `/v1/search` endpoint (`docs.litellm.ai/docs/search/`) rather than inventing a competing shape. LiteLLM has already solved and open-sourced the per-vendor request/response mapping problem for 12+ providers — reinventing that mapping wastes build time on a solved problem and makes SearchBench harder to adopt for anyone already on LiteLLM. The differentiated part SearchBench adds is entirely the routing *decision* (which vendor, based on what evidence), not the plumbing underneath it — positioning SearchBench's router as a routing-policy plug-in on top of LiteLLM's schema, or a drop-in alternative with the same interface, is both technically sensible and a plausible distribution channel (LiteLLM's own userbase is a warm audience already primed to want exactly this).

## Stack recommendation (given the founder's constraints)

Full-stack + ML/systems-capable solo founder, Apple Silicon Mac as primary hardware, rented cloud compute available, no dedicated infra budget. A pragmatic default: TypeScript/Node or Python for the runner and router API (either is fine given the founder's stated full-stack strength; Python has a slight edge if the judge-ensemble and classification logic end up wanting closer integration with ML tooling), Next.js for the dashboard (pairs naturally with Vercel), Supabase (Postgres) for storage, GitHub Actions for the weekly scheduled runner, and a simple background-job pattern (rather than an always-on server) for the runner itself, since it only needs to wake up once a week. Keep the router API itself as a lightweight, always-on service (a small always-on instance or a serverless function with reasonable cold-start behavior) since that's the piece real users will call synchronously.

## Build-order recommendation

Ship the runner and judge pipeline first, against a small (4-5 vendor) cleared list, and get real weekly data accumulating in public as early as possible — the elapsed-time credibility this buys compounds daily and cannot be caught up on later. Ship the dashboard second, as soon as there's at least a few weeks of real data to show (a dashboard with one week of data looks like a demo; a dashboard with six weeks of data looks like a running product). Ship the router SDK third, once the benchmark itself has enough of a public track record to make "route based on our scores" a credible pitch rather than a chicken-and-egg problem. This sequencing is also what the timeline in `07-build-plan.md` assumes.

## Open technical questions to resolve during build, not before

Exactly how aggressive the query-category classifier needs to be before routing decisions are trustworthy is an empirical question — start with a simple heuristic and measure before investing in anything more sophisticated. Whether to hard-cache vendor responses for a given (query, week) pair or re-fetch on every dashboard load is a cost/freshness tradeoff best resolved once real traffic patterns are visible. Rate-limit-aware fallback behavior (what the router does when a vendor's own rate limit is hit mid-request) needs concrete numbers from each cleared vendor's dashboard/docs that weren't fully available in this research pass for several vendors (see `03-legal-and-vendor-terms.md` open gaps) and should be confirmed directly against each vendor's developer documentation before the router's retry/fallback logic is finalized.
