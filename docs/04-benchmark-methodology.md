# 04 — Benchmark Methodology

## Design principle

Every existing LLM-judge framework surveyed (RAGAS, TruLens, DeepEval, Braintrust, LangSmith) converges on the same loop: run a baseline judge, measure its disagreement against a human-labeled gold subset, diagnose the specific bias or failure mode responsible, refine the prompt/rubric, and re-measure — repeating until agreement plateaus. None of them treat "write a judge prompt and ship it" as sufficient, and neither should SearchBench. This is the loop to build into the harness from week one, not bolt on later.

## Query taxonomy

Six categories, targeting 150-300 total queries (25-50 per category), each seeded from a real, appropriately-licensed dataset rather than hand-written from scratch wherever possible:

**Breaking news / freshness** — seed from **FreshQA** (Google, ACL Findings 2024), which is purpose-built with "fast-changing," "never-changing," and "false-premise" question categories and is itself updated weekly by its maintainers — a natural match for a benchmark that also refreshes weekly. Caution: FreshQA's GitHub README contains no explicit license grant, only a citation request. Treat this as "cite the source, use for question-prompt inspiration, do not redistribute the raw dataset" until the license question is resolved directly with the maintainers (contact address is in the README).

**General facts** — seed from **SimpleQA** (OpenAI, MIT license, 4,326 questions with reference URLs per question — ideal for grading citation quality, not just answer correctness) and **TriviaQA** (Apache 2.0). Note SimpleQA is already used as marketing collateral by Tavily itself in its self-benchmark, which makes it a credible, recognizable choice for this category.

**Multi-hop / research reasoning** — seed from **HotpotQA** (CC BY-SA 4.0, ~113,000 QA pairs, 2-hop questions requiring synthesis across two source pages) and **2WikiMultihopQA** (Apache-2.0, deeper, less-shortcuttable multi-hop chains built from Wikidata triples — arguably a better stress test than HotpotQA, which is known to have shortcut-solvable questions). Use both purely as question generators: score the live API's ability to find and connect the facts, not its match against the original closed corpus.

**Code / technical documentation** — no directly reusable licensed dataset was found (CodeRAG-Bench is built around static, pre-indexed code corpora, not live web search, and its license isn't stated in the repo). Hand-author roughly 25-40 "how do I do X in library Y at version Z" queries against real, dated library docs and changelogs. This category is worth the manual effort because it's exactly where freshness — SDK version drift — differentiates vendors most visibly.

**Local / shopping** — seed query phrasing from the **Amazon Shopping Queries Dataset / ESCI** (Apache-2.0, hundreds of thousands of real e-commerce queries with graded relevance judgments). Needs adaptation since the original task is product-catalog relevance rather than "does this API find the product on the live web," but the query language itself is directly reusable.

**Long-tail / research-adjacent** — hand-author a small original set rather than using FinanceBench (public sample is CC-BY-NC-4.0, non-commercial — a direct license conflict with a monetized product; the full set is gated/contact-only) or LegalBench-RAG (MIT-licensed but built around a closed, private-contract corpus with low transfer to open-web search). Do not build v1 on either without separately securing commercial-use permission.

**Datasets confirmed unsuitable as a scoring corpus (but occasionally useful as query-phrasing inspiration)**: BEIR (18 datasets, all closed/fixed-corpus, and BEIR's own project wiki explicitly disclaims responsibility for per-dataset licensing and fitness) and Natural Questions (Apache-2.0 but built around "read an entire Wikipedia article," i.e., closed-corpus). The general pattern across every academic dataset surveyed: none are built to grade a *live* web-search API end-to-end — they're uniformly built to grade retrieval against a fixed, pre-indexed corpus. The realistic and precedented approach (this is in fact what Tavily itself did in its own self-benchmark) is to borrow the questions and gold answers/reference URLs from permissively-licensed sets, then grade the live API's actual retrieved results against those gold answers directly, never reusing any dataset's closed corpus as the thing being searched.

## Judge design

**Use pointwise rubric scoring, not pairwise comparison.** Score each (query, vendor-response) pair independently against a rubric covering relevance, freshness, and citation quality in a single call. This keeps judge calls linear in queries × vendors rather than quadratic in queries × vendor-pairs — at 8-9 vendors, pairwise comparison would require C(9,2) = 36 comparisons per query instead of 9 pointwise calls, a 4x cost multiplier before any bias-mitigation redundancy is even added.

**Use a 3-judge cross-family ensemble, not a single judge.** This is not optional. A quantitative study using the Chatbot Arena dataset (33,000 human-labeled dialogue comparisons across 8 LLM judges) found that self-preference bias is real and that its root cause is not literal self-recognition but a preference for low-perplexity, "model-like" text — meaning the bias shows up even on text the judge didn't generate itself, as long as it's fluent in the judge's own house style. Since vendor search-answer synthesis may itself be produced by GPT/Claude/Gemini-class models under the hood, a single judge is not a safe design. Use one OpenAI-family, one Anthropic-family, and one Google-family model (cost-tier models are sufficient — Claude Haiku 4.5, Gemini 2.5 Flash, and GPT-5 mini class, not flagship pricing) and take the majority or median score across the three.

**Mitigate positional bias explicitly wherever any pairwise/comparative sub-metric is used** (for example, "which vendor's citation set is better" as a targeted spot-check rather than the primary scoring mechanism). Documented severity is serious: one analysis found GPT-4 as judge changed its verdict in 60-70% of comparisons when response order was simply swapped. The standard mitigation is to run every pairwise comparison in both orders and only count a real preference when both orders agree; disagreements get flagged for human review rather than silently resolved — expect this to convert roughly 30-50% of any pairwise comparisons attempted to "no verdict," which is a feature of the mitigation, not a bug to engineer away.

**Mitigate verbosity bias** with explicit length-normalization language in the rubric prompt, and report response length alongside the score so outliers are visible to anyone reading the published methodology.

**Calibrate monthly against a human-labeled gold set.** RAGAS's own alignment guide (the most detailed of the frameworks surveyed on this specific point) recommends 100-200 examples labeled by a domain expert as the target gold-set size, with a four-phase loop: baseline judge run, error analysis splitting false positives from false negatives, targeted prompt refinement aimed at the specific failure mode found, and iterative re-testing until agreement plateaus. Budget the founder's own time for this labeling in month one; it is the single highest-leverage thing that keeps "the judge said so" from becoming an unexamined black box.

## Refresh cadence

Run the full query set across all live vendors **weekly**, matching FreshQA's own weekly refresh rhythm. Rotate the freshness-bucket queries specifically on every cycle so vendors cannot overfit to a static set of "breaking news" questions. Weekly cadence is also the actual product differentiator versus every existing snapshot-in-time vendor self-benchmark — it needs real elapsed time running in public to be credible, not just code that's capable of running.

## Cost model

At a central-case volume of roughly 200 queries × 8.5 vendors ≈ 1,700 (query, vendor) pairs graded weekly, one judge call each (~1,500 input tokens covering the query, rubric, and the vendor's top retrieved results, plus ~250 output tokens for a numeric score and short rationale) against a 3-judge cross-family ensemble runs on the order of **$150-250/month**, using cost-tier models (Claude Haiku 4.5, Gemini 2.5 Flash, GPT-5-class mini/nano models) rather than flagship pricing. This is a first-principles planning estimate, not an observed real-world bill from an existing production system at this exact scale — no case study of anyone running an LLM-judge pipeline at this specific query/vendor/cadence combination was found. Instrument actual token usage from week one and correct the estimate empirically rather than trusting it blindly. For context, this judge-inference cost is small relative to the underlying vendor search-API query spend at the same volume (see `06-business-model.md`) and to compute/hosting — it is not the constraint that will decide whether this project is affordable to run solo.

## Open methodology gaps (explicit)

FreshQA's license status is unresolved and should be confirmed directly with its maintainers before building commercial tooling on top of the raw dataset (using it only as question-prompt inspiration is lower-risk in the meantime). The exact current size of 2WikiMultihopQA and the current exact QA-pair count of TriviaQA should be re-verified directly from the downloaded data files rather than trusted from this document's approximate figures. CodeRAG-Bench's license was not stated anywhere in its repo and should not be assumed open without checking the LICENSE file directly. Braintrust/autoevals' specific implementation detail for positional-bias mitigation (whether its comparative scorers auto-randomize order) was referenced in secondary commentary but not confirmed against the library's actual source — check before assuming it's handled for you. Underlying vendor search-API query costs at the target volume are a distinct cost line from judge inference and are covered separately in `06-business-model.md`, not in this document.
